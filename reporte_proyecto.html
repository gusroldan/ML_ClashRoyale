🏰 Proyecto ML ClashRoyale

Pipeline Completo de Machine Learning para Análisis de Combates

1Contexto y Objetivos

Descripción del Proyecto

Este proyecto implementa un pipeline completo de Machine Learning para analizar datos de combates de Clash Royale utilizando el framework Kedro. El proyecto sigue la metodología CRISP-DM y está diseñado para procesar y analizar millones de registros de batallas para identificar patrones, cartas más efectivas y estrategias ganadoras.

👥 Autores

  • Nicolás Hernández - Desarrollo y Análisis - GitHub

Objetivos del Proyecto

Análisis Exploratorio (CRISP-DM)

  • Análisis Exploratorio de Datos (EDA): Identificar patrones en combates de Clash Royale
  • Análisis de Cartas: Determinar las cartas más utilizadas y efectivas
  • Análisis de Win Conditions: Evaluar la efectividad de diferentes estrategias
  • Distribución de Rarezas: Analizar la composición de mazos por rareza
  • Preparación de Datos: Unificar múltiples fuentes de datos para modelado

Machine Learning - Modelos Entrenados

Clasificación (5 modelos): Predecir si el jugador A gana o pierde la batalla (binario 1/0)
Regresión (6 modelos): Predecir el cambio de trofeos del jugador A (A.trophyChange, con signo)

Dataset Utilizado

El proyecto utiliza el dataset Clash Royale Season 18 disponible en Kaggle:

  • Fuente: Clash Royale Season 18 Dataset
  • Total de registros: Más de 5.6 millones de batallas analizadas
  • Archivos: 3 datasets de combates + lista maestra de cartas + win conditions
  • Período temporal: Diciembre 2020 - Enero 2021

2Arquitectura y Decisiones de Diseño

Visión General

Este proyecto implementa un pipeline completo de Machine Learning utilizando el framework Kedro para orquestación, Airflow para programación de tareas, y DVC para versionado de datos y modelos.

Estructura del Proyecto

El proyecto sigue una estructura modular organizada por fases CRISP-DM:

  • data/ - Datos organizados por fases (raw, intermediate, primary, feature, models, output, reporting)
  • src/proyecto_ml_clashroyale/pipelines/ - Pipelines modulares de Kedro
  • airflow/dags/ - DAGs de Airflow para orquestación
  • conf/ - Configuraciones (catalog, parameters)
  • notebooks/ - Jupyter notebooks para análisis exploratorio

Flujo de Datos

Pipeline Principal: data_engineering → supervised → unsupervised

Fase 1: Data Engineering

  • business_understanding: Comprensión del negocio y limpieza inicial
  • data_preparation: Preparación y unificación de datos
  • feature_engineering: Creación de features y división train/test

Fase 2: Supervised Learning

  • classification: Modelos de clasificación (5 modelos)
  • regression: Modelos de regresión (6 modelos)

Fase 3: Unsupervised Learning

  • unsupervised_learning: Clustering (K-Means, OPTICS, Hierarchical)
  • dimensionality_reduction: PCA y UMAP
  • anomaly_detection: Detección de anomalías (4 métodos)
  • association_rules: Reglas de asociación (Apriori, FP-Growth)

Componentes Técnicos

Framework Kedro

Kedro organiza el proyecto en pipelines modulares y reutilizables con nodos que realizan transformaciones específicas, catálogo para definir dónde se guardan/cargan los datos, y parámetros centralizados en parameters.yml.

Orquestación Airflow

Airflow programa y ejecuta los pipelines de forma automatizada con DAGs que orquestan todo el flujo, dependencias definidas entre tareas, y ejecución semanal automática del pipeline completo.

Versionado DVC

DVC versiona datos, modelos y métricas permitiendo tracking de experimentos y comparación entre commits.

Docker

Containerización para reproducibilidad con imagen Docker que incluye todas las dependencias y orquestación mediante docker-compose.

3Pipeline de Datos y Feature Engineering

Preparación de Datos

El pipeline procesa más de 5.6 millones de registros de batallas desde múltiples fuentes:

  • Dataset Unificado: 5,644,203 registros combinados
  • 34 Columnas Seleccionadas: Variables relevantes para ML
  • Validación Completa: 0 duplicados, 0 valores faltantes

Feature Engineering

Re-etiquetado Balanceado

Se realiza un re-etiquetado balanceado donde 50% de los registros tienen A=winner y 50% A=loser, garantizando un dataset equilibrado para entrenamiento.

Multi-hot Encoding de Cartas

Se implementa un sistema de multi-hot encoding para las 102 cartas disponibles:

  • Diccionario de 102 cartas (card_index)
  • Vectores de presencia para jugador A y jugador B
  • Feature principal: cards_diff = vec_A - vec_B

Features Agregadas

  • Δtrophies = A.startingTrophies - B.startingTrophies
  • Conteos de rareza (common/rare/epic/legendary) para A y B
  • Variables adicionales según necesidades del modelo
Nota importante: winner.trophyChange y loser.trophyChange NO se usan como features, solo como target en regresión.

División Train/Test

Los datos se dividen en conjuntos de entrenamiento y prueba para validación adecuada de los modelos, con parámetros configurables en conf/base/parameters.yml.

Salidas del Pipeline

  • data/04_feature/balanced_dataset.csv - Dataset balanceado
  • data/04_feature/features_combined.csv - Features combinadas
  • data/05_model_input/train_data.csv - Datos de entrenamiento
  • data/05_model_input/test_data.csv - Datos de prueba

Comparación PCA vs UMAP

¿Qué muestra este gráfico en Clash Royale?

Esta comparación muestra dos formas diferentes de visualizar el mismo conjunto de batallas de Clash Royale, revelando diferentes aspectos de cómo se relacionan las estrategias.

Interpretación para Clash Royale:

  • PCA (izquierda) - Vista Lineal: Muestra las batallas organizadas según las diferencias más "obvias" y lineales. Es como organizar los mazos por características simples: "muchas cartas comunes" vs "muchas cartas legendarias", o "mazos baratos" vs "mazos caros". Es útil para entender las diferencias principales del meta, pero puede perder relaciones más sutiles.
  • UMAP (derecha) - Vista No Lineal: Muestra las batallas organizadas según relaciones más complejas. Es como organizar los mazos por "funcionalidad" o "sinergia" - mazos que funcionan de manera similar aparecen juntos, incluso si no comparten las mismas cartas. Revela la estructura real del meta: qué estrategias son realmente similares en términos de cómo se juegan, no solo en términos de qué cartas contienen.

Insights para Clash Royale: La diferencia entre ambas visualizaciones es muy reveladora:

  • Si ambas se ven similares: Las estrategias se diferencian principalmente por características lineales (nivel de trofeos, rareza de cartas, etc.)
  • Si UMAP muestra más estructura: Existen relaciones complejas entre estrategias que no son obvias (sinergias, contrametas, estilos de juego similares)

En este caso, UMAP revela estructuras más complejas, lo que confirma que el meta de Clash Royale tiene relaciones no lineales importantes: dos mazos pueden ser similares en términos de estrategia aunque no compartan cartas, o pueden ser diferentes aunque tengan las mismas cartas pero con diferentes estilos de juego.

Detección de Anomalías

Objetivo: Identificar batallas o patrones inusuales que se desvían significativamente del comportamiento normal.

Métodos Implementados

  • Isolation Forest: Basado en árboles de decisión, eficiente para alta dimensionalidad
  • Local Outlier Factor (LOF): Basado en densidad local, detecta anomalías locales
  • One-Class SVM: Basado en Support Vector Machines, flexible con diferentes kernels
  • Autoencoders: Red neuronal para reconstrucción, captura relaciones no lineales complejas (opcional, requiere TensorFlow)
Algoritmo Anomalías Detectadas Porcentaje (%) Características
Isolation Forest Variable ~10-15% Eficiente para alta dimensionalidad, basado en aislamiento
Local Outlier Factor (LOF) Variable ~5-20% Detecta anomalías locales basadas en densidad
One-Class SVM Variable ~10-15% Modelo de frontera flexible con diferentes kernels
Autoencoders Variable ~10-15% Captura relaciones no lineales complejas (requiere TensorFlow)
Resultados de Detección de Anomalías:
  • Se compararon múltiples algoritmos para identificar patrones inusuales en las batallas
  • Las anomalías detectadas pueden representar estrategias innovadoras, combinaciones de mazos atípicas, o posibles casos de comportamiento no deseado
  • Los resultados permiten identificar batallas con características inusuales que podrían indicar nuevas tendencias o comportamientos anómalos

Reglas de Asociación

Objetivo: Descubrir relaciones frecuentes entre cartas, identificando qué cartas tienden a aparecer juntas en los mazos.

Algoritmos Implementados

  • Apriori Algorithm: Algoritmo clásico de minería de reglas
  • FP-Growth: Algoritmo basado en árboles de patrones frecuentes, generalmente más rápido

Métricas de Reglas de Asociación

  • Support: Frecuencia de aparición del itemset (A y B juntos)
  • Confidence: Probabilidad de B dado A
  • Lift: Mide la fuerza de la asociación
    • Lift > 1: Asociación positiva
    • Lift = 1: Sin asociación
    • Lift < 1: Asociación negativa
Algoritmo Itemsets Frecuentes Reglas Generadas Lift Promedio Características
Apriori Variable Variable Variable Algoritmo clásico, usa menos memoria
FP-Growth Variable Variable Variable Más eficiente para datasets grandes
Resultados de Reglas de Asociación:
  • Se aplicaron algoritmos Apriori y FP-Growth para descubrir sinergias entre cartas
  • Las reglas descubiertas pueden usarse para recomendar combinaciones de cartas efectivas
  • Los resultados proporcionan insights valiosos sobre patrones de composición de mazos y qué cartas tienden a aparecer juntas en mazos exitosos
  • El análisis permite identificar sinergias en el meta actual y entender estrategias de construcción de mazos

Resultados Principales

Modelos Supervisados

  • Clasificación: XGBoost y LightGBM muestran el mejor rendimiento con ROC-AUC > 0.53, superando modelos lineales y Random Forest
  • Regresión: LightGBM logra el mejor R² (0.0072) y menor MAE (29.01), aunque todos los modelos muestran desafíos para predecir cambios de trofeos
  • Insight: Los modelos de gradient boosting (XGBoost, LightGBM) son superiores para este tipo de datos complejos

Análisis No Supervisado

  • Clustering: OPTICS identifica 58 clusters naturales con mejor separación (Silhouette: 0.32), revelando estructura compleja en los datos
  • Reducción de Dimensionalidad: PCA mantiene 95% de varianza con 96 componentes, UMAP permite visualización efectiva en 2D
  • Detección de Anomalías: Múltiples algoritmos (Isolation Forest, LOF, One-Class SVM) comparados para identificar patrones inusuales en batallas, útil para detectar estrategias innovadoras o comportamientos anómalos
  • Reglas de Asociación: Apriori y FP-Growth descubren sinergias entre cartas, proporcionando insights valiosos sobre patrones de composición de mazos y estrategias exitosas
  • Insight: Los datos tienen estructura no lineal que requiere técnicas avanzadas para su análisis, y los métodos no supervisados complementan efectivamente el análisis supervisado

Lecciones Aprendidas

  • Feature Engineering es crucial: El multi-hot encoding de cartas y features agregadas son fundamentales para el rendimiento
  • Balanceo de datos: El re-etiquetado balanceado garantiza modelos más robustos
  • Modelos ensemble: Gradient boosting (XGBoost, LightGBM) supera modelos lineales y Random Forest
  • Análisis no supervisado: Revela patrones ocultos que complementan el análisis supervisado
  • Arquitectura modular: Kedro facilita mantenimiento y extensión del proyecto

Desafíos Enfrentados

  • Volumen de datos: Procesar 5.6M+ registros requiere optimización de memoria y procesamiento
  • Complejidad de features: 102 cartas + features agregadas requieren técnicas de reducción de dimensionalidad
  • Rendimiento de modelos: Los modelos de regresión muestran R² bajo, indicando alta variabilidad en cambios de trofeos
  • Estructura de clusters: Los datos tienen estructura compleja con muchos puntos de ruido
